# ADR-002 — Estrutura de Pacotes: Módulo Primeiro, Camadas Dentro

* **Status:** Accepted
* **Date:** 2026-10-02
* **Decision Type:** Architecture
* **Related:** `docs/adr/ADR-001.md`, `docs/architecture/ARCHITECTURE.md`, `docs/architecture/MODULES.md`

---

## 1. Context

O ADR-001 definiu um Modular Monolith com Clean Architecture, e o `MODULES.md` definiu quatro módulos de
negócio (Workflow Definition, Workflow Execution, Rules e Audit). Faltava decidir como esses dois eixos
— módulos e camadas — se traduzem em pacotes Java, e como os limites são verificados.

---

## 2. Decision

O código é organizado **primeiro por módulo e, dentro de cada módulo, por camada**:

```text
com.pablohenrique.workflowengine
│
├── definition/                 Workflow Definition
│   ├── contract/               contrato público do módulo
│   ├── domain/                 aggregates, value objects, erros de domínio
│   ├── application/            casos de uso e portas
│   ├── infrastructure/         adapters (persistência JPA)
│   └── interfaces/rest/        controllers, DTOs, tradução de erros
│
├── execution/                  Workflow Execution (mesma estrutura)
├── rules/                      Rules (contract, domain, infrastructure)
├── audit/                      Audit (mesma estrutura)
│
└── infrastructure/             preocupações técnicas transversais
    ├── config/                 relógio
    ├── security/               autenticação e autorização HTTP
    ├── web/                    erros globais, correlação de requisições
    └── openapi/                documentação da API
```

Regras:

1. **`contract` é a única porta de entrada de um módulo.** Código de fora do módulo só pode depender do
   pacote `contract` dele.
2. **`domain` e `contract` não dependem de frameworks** (Spring, JPA, Jackson, Servlet).
3. **Dentro do módulo, as dependências apontam para o domínio:** `interfaces → application → domain` e
   `infrastructure → application/domain`. `interfaces` não acessa `infrastructure`.
4. **A camada `application` pode usar Spring** para injeção, transações e paginação (`Page`/`Pageable`).
   O domínio permanece puro.
5. **Não há ciclos entre módulos.**

O grafo de dependências entre módulos é:

```text
execution ──► definition.contract
execution ──► rules.contract
definition ─► rules.contract        (vocabulário de Rule usado na definição das Transitions)
definition ─► audit.contract
execution ──► audit.contract
```

Essas regras são verificadas automaticamente por `ArchitectureTest` (ArchUnit) a cada build.

---

## 3. Alternatives Considered

### 3.1 Camada primeiro, módulos dentro (`domain/definition`, `application/definition`, ...)

Evidencia as camadas, mas espalha cada módulo por toda a árvore e dificulta enxergar — e extrair — um
módulo como unidade.

**Decisão:** Rejeitada.

### 3.2 Módulos Maven separados

Daria isolamento em tempo de compilação, ao custo de um build multi-módulo desde o início.

**Decisão:** Adiada. Os testes de arquitetura dão a mesma garantia com menos cerimônia; a separação em
módulos Maven fica registrada no backlog técnico para quando houver necessidade.

### 3.3 Spring Modulith

Oferece verificação de módulos e eventos entre módulos, mas introduz uma dependência nova para algo que o
ArchUnit, já previsto na stack, resolve.

**Decisão:** Rejeitada por ora (AC-007).

---

## 4. Consequences

### Positivas

- cada módulo é localizável e potencialmente extraível como unidade;
- violações de limite falham o build, e não dependem de revisão manual;
- o domínio é testável sem subir contexto Spring nem banco.

### Negativas

- há mapeamento explícito entre domínio e entidades JPA, e entre domínio e DTOs;
- `definition` depende de `rules.contract`, relação que não constava do diagrama inicial do `MODULES.md`
  (documento atualizado junto com este ADR).
