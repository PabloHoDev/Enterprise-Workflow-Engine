# ADR-007 — Módulo Identity e Sessão Segura para o Console Web

* **Status:** Accepted
* **Date:** 2026-10-03
* **Decision Type:** Security
* **Supersedes:** ADR-005
* **Related:** `docs/architecture/SECURITY.md`, `docs/adr/ADR-008.md`

---

## 1. Context

O ADR-005 adotou HTTP Basic com usuários fixos na configuração, aceitando limitações conhecidas (TD-001 a
TD-003): sem gestão de contas, sem bloqueio por tentativas, sem limite de requisições e sem auditoria de
negações de acesso.

Duas mudanças tornaram essas limitações inaceitáveis:

1. o projeto passou a ter um **console web** (ADR-008). HTTP Basic não serve para navegador: o navegador
   guarda a credencial, exibe o próprio diálogo de login e não oferece logout;
2. o objetivo declarado do projeto é demonstrar **práticas profissionais de segurança**.

Continua sem existir um provedor de identidade (Keycloak, Entra ID…) disponível para desenvolvimento e
demonstração.

---

## 2. Decision

### 2.1 Novo módulo de negócio `identity`

Contas ficam no PostgreSQL (`app_user`, `app_user_role`), com:

- senha em **BCrypt** (`DelegatingPasswordEncoder`, que permite trocar de algoritmo sem invalidar senhas);
- **política de senha** alinhada ao NIST SP 800-63B: mínimo de 12 caracteres, sem regras de composição
  obrigatória, sem repetição trivial e sem conter o nome de usuário;
- **bloqueio temporário** após 5 senhas erradas consecutivas (15 minutos, configurável), com registro
  protegido por `SELECT … FOR UPDATE` para não perder contagens sob ataque paralelo;
- gestão pelo administrador (criar, alterar papéis, ativar/desativar, redefinir senha, desbloquear);
- troca da própria senha, exigindo a senha atual;
- **invariantes de administração**: sempre existe ao menos um administrador ativo, e um administrador não
  pode remover o próprio acesso.

As contas iniciais vêm de `workflow-engine.identity.seed-users`; a aplicação não sobe sem um administrador.

### 2.2 Console web: sessão em cookie, nunca token no navegador

- `POST /api/v1/auth/login` abre uma sessão cujo identificador vai em cookie `EWE_SESSION`
  **HttpOnly**, `SameSite=Lax` e `Secure` em produção. O JavaScript nunca vê a credencial.
- A sessão é guardada no **PostgreSQL** (Spring Session JDBC): as instâncias continuam sem estado local
  (DEPLOYMENT.md, DP-006) e uma sessão pode ser encerrada de qualquer instância.
- **CSRF** com o padrão *double submit* do Spring Security para SPAs: cookie `XSRF-TOKEN` (legível pela
  própria origem, `SameSite=Strict`) devolvido no header `X-XSRF-TOKEN`.
- A cada login: **novo id de sessão** (contra fixação) e **novo token CSRF**.
- Expiração por inatividade em 30 minutos.
- Mudança de papéis, desativação, redefinição ou troca de senha **encerram todas as sessões** do usuário.

### 2.3 Integrações: HTTP Basic sem sessão

Clientes de integração continuam usando HTTP Basic. Requisições com header `Authorization` não carregam
credencial ambiente, por isso dispensam CSRF. As mesmas contas, o mesmo bloqueio e a mesma auditoria valem
para os dois canais.

### 2.4 Proteções transversais

| Proteção                                    | Implementação                                                 |
| ------------------------------------------- | ------------------------------------------------------------- |
| Limite de falhas de login por origem         | 10 falhas por minuto por IP → `429` com `Retry-After`         |
| Mensagem de falha uniforme                   | usuário inexistente, senha errada, conta bloqueada ou desativada → mesma resposta |
| Tamanho máximo de requisição                 | 256 KB → `413`                                                |
| Cabeçalhos de navegador                      | CSP restritiva, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, `nosniff` |
| Auditoria de autenticação e acesso           | `LOGIN_SUCCEEDED`, `LOGIN_FAILED`, `ACCOUNT_LOCKED`, `LOGOUT`, `ACCESS_DENIED`, operações sobre contas |

## 3. Alternatives Considered

### 3.1 OAuth2/OIDC com provedor externo

Continua sendo o destino para um ambiente corporativo real (SSO, MFA, políticas centralizadas). Exige um
provedor rodando para desenvolver, testar e demonstrar. **Adiada** (TB-013): o domínio depende só de
`Actor(id, roles)`, e o console só conhece `/api/v1/auth/*`, então a troca fica contida.

### 3.2 JWT guardado no navegador (localStorage)

Exposto a qualquer XSS, sem revogação imediata e com renovação complexa. **Rejeitada.** A recomendação
atual para aplicações de navegador é manter o token fora do JavaScript (padrão BFF / cookie HttpOnly).

### 3.3 Sessão em memória da instância

Mais simples, mas quebraria a escalabilidade horizontal e o encerramento de sessões por outra instância.
**Rejeitada.**

---

## 4. Consequences

### Positivas

- credenciais e sessões tratadas segundo as práticas atuais (OWASP ASVS nível 2 como referência);
- uma única fonte de contas para o console e para integrações;
- revogação imediata de acesso;
- trilha de auditoria completa de autenticação.

### Negativas

- a aplicação passa a guardar credenciais: o banco precisa da mesma proteção de um repositório de senhas;
- o limite de falhas por origem é local à instância (TD-009);
- sem MFA nem SSO até a adoção de um provedor de identidade.
