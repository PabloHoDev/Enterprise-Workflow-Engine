# ADR-008 — Console Web como SPA Servida pela Própria Aplicação

* **Status:** Accepted
* **Date:** 2026-10-03
* **Decision Type:** Architecture
* **Related:** `docs/adr/ADR-001.md`, `docs/adr/ADR-007.md`, `docs/frontend-status.md`

---

## 1. Context

Os requisitos iniciais deixavam o "frontend completo" fora do escopo, e a única interface era o Swagger UI.
Para demonstrar o produto de ponta a ponta, foi aprovado um **console administrativo**: definições,
versões, execuções, ações, histórico, auditoria e gestão de usuários. O editor visual de arrastar e soltar
(BPMN) continua fora do escopo.

Era preciso decidir a tecnologia e, principalmente, como o console se relaciona com a aplicação.

---

## 2. Decision

### 2.1 Uma SPA estática, na mesma origem da API

- **React 19 + TypeScript (estrito)**, empacotado com **Vite**.
- **TanStack Query** para dados do servidor (cache, revalidação, estados de carregamento e erro).
- **React Router** para rotas; filtros e paginação ficam na URL.
- **Tailwind CSS 4** para estilo, com tema claro e escuro; fontes do sistema (nada carregado de terceiros).
- Código em `frontend/`; o build é copiado para `classpath:/static` pelo `Dockerfile`.

A aplicação Spring entrega o `index.html` para as rotas do console e os arquivos com hash em `/assets`
(cache de um ano). Console e API ficam na **mesma origem**:

- não há CORS a configurar nem a errar;
- o cookie de sessão é `HttpOnly` e `SameSite` sem exceções (ADR-007);
- a CSP pode ser `default-src 'self'`;
- continua havendo **uma única unidade de deploy** (DP-001).

Em desenvolvimento, o servidor do Vite faz proxy de `/api` para a aplicação: para o navegador, também é a
mesma origem.

### 2.2 Regras ficam no servidor

O console não decide regra de negócio. Ele exibe as ações que a API declara disponíveis, mostra as regras
de cada transição e traduz as respostas de erro. Esconder um botão é conveniência; a autorização efetiva é
sempre da API.

### 2.3 Qualidade como parte do build

- ESLint e `tsc` estrito;
- testes unitários com Vitest e Testing Library;
- testes end-to-end com Playwright contra a aplicação real, incluindo verificação automática de
  acessibilidade (axe, WCAG 2 AA), tema escuro e tela de 360 px.

---

## 3. Alternatives Considered

### 3.1 Next.js (SSR)

Exigiria um servidor Node em produção: duas unidades de deploy, sessão compartilhada entre elas e mais
infraestrutura, sem ganho real para um console autenticado que não precisa de SEO. **Rejeitada.**

### 3.2 Aplicação em repositório e domínio separados

Obrigaria CORS e cookies `SameSite=None`, ampliando a superfície de ataque. **Rejeitada.**

### 3.3 Server-side rendering com Thymeleaf

Menos peças, porém interação limitada e uma experiência abaixo do esperado para um portfólio de produto.
**Rejeitada.**

### 3.4 Biblioteca de componentes pronta (MUI, Ant Design)

Aceleraria telas, mas adicionaria peso e estilo genérico. Componentes próprios e pequenos sobre Tailwind
cobrem as necessidades atuais. **Rejeitada por ora.**

---

## 4. Consequences

### Positivas

- uma imagem, um processo, uma origem: operação e segurança mais simples;
- o console exercita a API pública; não há atalhos internos.

### Negativas

- o build da imagem passa a depender de Node (estágio próprio no `Dockerfile`);
- para rodar a aplicação localmente com o console sem Docker, é preciso o build do front
  (`npm run build`) e a propriedade `workflow-engine.web.console-location`.
