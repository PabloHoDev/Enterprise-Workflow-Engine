# ADR-006 — Decisões de Modelagem do Domínio na Primeira Implementação

* **Status:** Accepted
* **Date:** 2026-10-02
* **Decision Type:** Domain
* **Related:** `docs/product/DOMAIN.md`, `docs/product/BUSINESS_RULES.md`, `docs/product/USE_CASES.md`

---

## 1. Context

Os documentos de produto descrevem o domínio em nível conceitual e deixam pontos em aberto de propósito
("a representação técnica será definida posteriormente"). Ao implementar, foi preciso fechar esses pontos.
Este ADR registra cada escolha para que não fique implícita no código.

---

## 2. Decisions

### 2.1 Step é representado por State + Transitions

O `DOMAIN.md` define Step como a unidade de processo; o `MODULES.md` lista apenas Version, State e
Transition como conceitos do módulo. Na implementação, **um Step corresponde a um State não terminal
junto das Transitions que partem dele**. "Executar o Step" (RF-010) é executar uma ação disponível no
State atual. Não existe uma entidade `Step` separada.

### 2.2 A estrutura de uma versão é imutável desde a criação

Uma versão nasce completa e validada; depois disso só o seu **status** muda
(`DRAFT → ACTIVE ⇄ INACTIVE`). Qualquer alteração de estrutura é uma nova versão (BR-007). Isso torna
BR-006 verdadeira por construção, e não por verificação.

Consequência: não existe versão "incompleta". A validação estrutural (BR-002, BR-004) acontece na
criação da versão, e não na ativação.

### 2.3 No máximo uma versão ativa por definição (BR-041)

Ativar uma versão retira automaticamente a anteriormente ativa de novas execuções. Assim, "a versão
aplicável" ao criar um Workflow (UC-006) é sempre inequívoca. Workflows em andamento não são afetados.

### 2.4 Status do ciclo de vida separado do State do processo

Um Workflow possui dois atributos distintos:

- `currentState`: um State definido pelo processo (`PENDING_APPROVAL`, `APPROVED`...);
- `status`: o ciclo de vida da execução — `CREATED`, `RUNNING`, `COMPLETED`, `CANCELLED`.

`COMPLETED` é atingido ao entrar em um State terminal da definição. Estados como `APPROVED` e `REJECTED`
são States terminais do processo, não status do motor.

### 2.5 Cancelamento é uma operação do motor (BR-042)

O cancelamento não é uma Transition da definição. É permitido enquanto o `status` não for terminal e
leva o Workflow a `CANCELLED`, **preservando o `currentState`** em que a execução parou — informação
útil para entender onde o processo foi interrompido.

### 2.6 Criar e iniciar são operações distintas

Seguindo UC-006 e UC-007: criar posiciona o Workflow no State inicial com status `CREATED`; iniciar o
leva a `RUNNING`. Ações só são aceitas em `RUNNING`.

### 2.7 Execution é registrada como entrada do History

O conceito de Execution ("a realização de uma ação ou transição") é materializado pela própria entrada
de History, que guarda ação, States de origem e destino, Actor e momento. Não há uma entidade separada.

### 2.8 Rules são condições declarativas sobre as variáveis do Workflow

Uma Rule é `campo operador valor`, avaliada de forma determinística (BR-024) sobre as variáveis da
execução. Todas as Rules de uma Transition devem ser satisfeitas (BR-021). Uma variável ausente nunca
satisfaz uma Rule. Uma ação pode enviar variáveis; elas participam da avaliação e só são mantidas se a
Transition for efetivada (BR-022).

Roteamento condicional é modelado com ações distintas a partir do mesmo State (por exemplo, `approve`
e `send-to-finance`), cada uma com suas Rules: a combinação `(State de origem, ação)` é única (BR-043).

---

## 3. Alternatives Considered

- **Entidade `Step` própria**, com Transitions ligando Steps: aproxima-se de BPMN, mas duplica o papel
  do State sem atender a nenhum requisito atual. O `DOMAIN.md` já adia `Task` pelo mesmo motivo.
- **Versões em rascunho editáveis:** exigiria um ciclo de edição e validação na ativação. Pode ser
  introduzido depois sem quebrar o modelo; registrado no backlog técnico.
- **Várias versões ativas simultâneas:** exigiria uma regra de seleção de versão na criação do Workflow.
- **`CANCELLED` como State obrigatório em toda definição:** poluiria todas as definições com um estado
  e transições de cancelamento a partir de cada State.

---

## 4. Consequences

- o modelo implementado é menor que o modelo conceitual, sem contradizê-lo;
- as regras BR-041 a BR-045 foram acrescentadas ao `BUSINESS_RULES.md`;
- o `DOMAIN.md` continua sendo a referência conceitual; este ADR é a ponte para o código.
